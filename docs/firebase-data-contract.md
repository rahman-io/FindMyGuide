# Firebase data contract (draft v1)

The GitHub Pages build remains a local-data prototype. These fixtures and rules prepare a later Firebase migration; they do not enable Firebase, authentication, inventory, or payments. Do not import demo reviews/messages or unlicensed reference images into production.

## Collections and ownership

| Path | Purpose | Source/owner |
| --- | --- | --- |
| `users/{uid}` | Non-sensitive profile preferences | Firebase Auth UID |
| `users/{uid}/wishlists/{experienceId}` | Saved activity IDs | That user |
| `users/{uid}/messages/{messageId}` | Private inbox | Server writes, user reads |
| `users/{uid}/recommendationEvents/{eventId}` | Private behavior signals for personalization | That user creates; trusted service aggregates |
| `conversations/{conversationId}` | Private conversation summary and participant IDs | Participants; server controls lifecycle |
| `conversations/{conversationId}/messages/{messageId}` | Private chat messages and read receipts | Conversation participants |
| `organizations/{orgId}` | Operator/provider profile | Admin-created |
| `organizations/{orgId}/members/{uid}` | Organization membership and roles array | Admin/server-created |
| `experiences/{experienceId}` | Public catalog and editable draft content | One `organizationId` |
| `experiences/{experienceId}/slots/{slotId}` | Date/time, capacity, price overrides | Trusted booking service |
| `bookings/{bookingId}` | User, organization, slot, price snapshot, state | Trusted booking service |
| `guideAssignments/{assignmentId}` | Guide's limited itinerary data | Trusted service |
| `reviews/{reviewId}` | Activity feedback and moderation state | Trusted service |
| `media/{mediaId}` | Alt text, Storage path, rights and publication state | Trusted media workflow |
| `destinations/{id}`, `attractions/{id}` | Home/search tiles | Admin-curated |
| `socialProfiles/{uid}` | Public community identity and bio | User edits own public fields; admin assigns role |
| `socialProfiles/{uid}/followers/{followerUid}` | Follow relationship | Follower creates/removes own edge |
| `socialPosts/{postId}` | Caption, author, location, media reference and moderation status | Author creates/edits own post; admin moderates |
| `socialPosts/{postId}/likes/{uid}` | Like relationship | That user |
| `socialPosts/{postId}/comments/{commentId}` | Public comments | Author edits/deletes own comment; admin moderates |
| `users/{uid}/socialSaves/{postId}` | Private saved posts | That user |
| `socialReports/{reportId}` | User reports for review | Reporter creates; admin reviews/resolves |

The shape of demo catalog documents is generated by `src/features/experiences/firebase-documents.js` from the current local catalog and pricing fixtures. Amounts are integer cents with an explicit currency (`USD` in the demo); popularity/rating counts are numeric; `schemaVersion` supports later migrations. Stable document IDs match the current activity IDs so existing `#/experience/:id` links and wishlist references can survive migration. `demoTimeOptions` is UI-only sample data: real availability belongs in slot documents, not in the experience document.

The local recommendation engine in `src/features/recommendations/repository.js` is a non-LLM hybrid ranker. It combines catalog quality signals with private local behavior events such as views, searches, wishlist changes, and positive Vibes engagement. Social signals always carry the canonical `experienceId` of the linked Discover item, so a like, save, comment, or attached post can influence recommendations without mixing social opinions into official ratings. `toRecommendationFirebaseFixture()` exports the same event shape for later migration. Demo events use the placeholder `demo-user` only and must not be imported as real customer behavior.

Generated experiences and media are `draft` by default. The current UI still displays its local catalog; the draft status protects against accidentally publishing unreviewed demo content during a future import.

Media fixture `previewUrl` points to bundled files and is **not** a permanent URL or Storage path. Upload only licensed media, assign a Storage path and verified rights, then publish its metadata. Local screenshot-derived images have `licenseStatus: unverified` and `status: draft` on purpose. The current static map image and login illustration are app assets, not geospatial or operator-uploaded data.

## Role/access matrix

| Action | Guest | User | Assigned guide | Operator owner/manager | Admin |
| --- | --- | --- | --- | --- | --- |
| Read published catalog | Yes | Yes | Yes | Yes | Yes |
| Read own profile/wishlist/messages | No | Own only | Own only | Own only | Yes |
| Read draft experience | No | No | Assigned only | Own organization | Yes |
| Read booking personal details | No | Own only | No | Own organization | Yes |
| Read guide itinerary | No | No | Own assignment | Own organization | Yes |
| Create/update experience, slot, booking, payment state or review moderation | No | No | Via trusted service | Via trusted service | Admin/trusted service |
| Assign roles or organization membership | No | No | No | No | Admin/trusted service |

An authenticated person can have several organization memberships; do not put one self-editable `role` field in their profile. Only a trusted Admin SDK process may assign the global `admin` custom claim or membership documents. UI hiding is not authorization. Firestore/Storage rules provide the initial client boundary; trusted server/Admin SDK code **bypasses** these rules and must perform its own role, ownership, input, price, and capacity checks.

## Migration sequence

1. Create a Firebase project and separate development/staging/production environments; supply public Firebase web config through environment-specific configuration. No private service account goes into GitHub Pages or the browser.
2. Validate and enrich the fixture catalog: real organization ownership, guide assignments, dates/time zones, address/coordinates, age limits, cancellation terms, localized text, and media rights. Review every item before `published` status.
3. Create Auth users and trusted membership/role assignment. Replace local profile and wishlist persistence with UID-scoped repositories. Never migrate the placeholder identity or pretend demo reviews are verified.
4. Upload licensed images to Storage; replace `previewUrl` with `storagePath`/approved delivery URLs. Preserve gallery order and alt text.
5. Add date-specific slots and a trusted booking/quote endpoint. Recalculate the final total server-side in cents, reserve capacity atomically, record a price snapshot, and integrate an actual payment provider. The Firebase client is not a payment processor.
6. Replace synchronous local catalog reads with loading/error-aware Firebase repositories; preserve a clearly marked offline/read-only fallback if desired. Add needed Firestore indexes for actual queries.
7. Run `npm run test:rules` with Firebase CLI installed. Emulator tests currently cover guest, user, assigned guide, owner, and admin access; cross-user reads; role escalation; draft visibility; and upload type. Extend them for manager, upload-size limits, queries, and overbooking before production. Deploy rules before live data.

`firestore.rules`, `storage.rules`, and `firebase.json` are conservative scaffolding, not production approval. Emulator rule tests are local-only and do not deploy anything. No role-claim setup or payment function is connected yet.

## Community demo and Firebase migration

The Community tab uses six fictional demo profiles and seeded posts/interactions. A tester may switch demo profiles to see both sides of likes, follows, saves, comments and reports. Their changes and device-selected images are stored **only in that browser's localStorage**, not shared between phones or authenticated. The account switcher is explicitly for testing and must be removed when Firebase Auth is connected; it is not an impersonation feature for production. Device photos are compressed locally for the demo, with no upload to a server.

`src/features/social/repository.js` exports `toSocialFirebaseFixture()`. Its output separates profiles, posts, likes, saves, comments, follows and reports into documents with stable IDs, and includes a computed `moderationQueue` for admin review. A post may include an optional `experienceId` that links it back to Discover; the detail page can show these community recommendations and users can create a linked post directly from that experience. Social likes, saves, comments and posts also produce private recommendation events, while official booking reviews remain a separate verified-review source. `src/features/social/intelligence.js` provides the local Vibes Intelligence layer: personalized post ranking, topic/trending extraction, related-post matching, people-to-follow matching, notification priority, and deterministic safety scoring for admin review. Migrated posts are deliberately marked `draft`, and `media.storagePath` remains null: first upload media with rights/consent verified, then assign a user-owned Storage path and publish approved content. Never import fictional demo accounts as actual Firebase Auth users, and never label demo comments or engagement as real customer activity. The historical timestamps and relationship counts are synthetic.

Production clients must use Firebase Auth UID as the actor, store photos at `public/social/{uid}/{fileName}`, and use Firestore subcollections/UID-scoped saves rather than keeping `likedBy`/`savedBy` arrays on each post. Admin moderation can read reports and change publication status; posts do not require admin preapproval. Add server-side rate limiting, spam/abuse detection, pagination, file scanning, usernames uniqueness, notification delivery, counters, and proper deletion/appeal workflows before public launch. Video/reels are not part of this image-post demo.

## Recommendation engine migration

Discover currently ranks “Picked for you” locally with deterministic scoring: rating/review quality, featured/popular status, matching city searches, explored cities, labels, price affinity, duration affinity, and wishlist exclusions. Each recommendation includes a short explanation for the user. This is intentionally not an LLM call and has no per-request model cost.

After Firebase Auth is connected, write only the authenticated user's events to `users/{uid}/recommendationEvents/{eventId}`. Allowed social event types are `social_like`, `social_save`, `social_comment`, `social_post`, and `social_booking_open`; each linked event uses the Discover experience ID, not the social post ID, as its `experienceId`. Smart Trip Intent and itinerary previews are exported as draft, user-scoped planning documents; final availability, capacity, price, and booking eligibility must be recalculated by a trusted service. A trusted aggregation job should calculate rolling preferences, popularity windows, diversity limits, and experiment variants; the client must not be allowed to alter its own aggregate score or recommendation model. Add consent, retention/deletion controls, abuse filtering, cold-start onboarding, offline fallback, and A/B evaluation before using recommendations for commercial ranking.

## Inbox and chat demo

The Discover Inbox now combines seeded travel updates with private demo conversations. Conversations are stored locally under `lombok-chat-demo-v1`; switching a demo social account changes which participant threads are visible. `src/features/messaging/repository.js` exports `toMessagingFirebaseFixture()`, separating conversation summaries from message documents so the local demo can be migrated without changing the UI data shape.

When Firebase Auth is connected, read and write only conversations where the authenticated UID is in `participantIds`. The client may create a message only with its own `senderId`; server-side validation should enforce block/report state, rate limits, message length, notification delivery, and deletion/retention policy. Conversation summaries should be updated by a trusted service or a narrowly scoped participant update, while admin access remains for moderation and support.
